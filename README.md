# منصة فعاليات كت التفاعلية (Kick Events Platform)

منصة عربية بالكامل (RTL) لصناعة **فعاليات تفاعلية حية** داخل بث Kick:
مسابقات أسئلة، تحديات سرعة، ومواجهات فرق — يشترك المشاهدون وينافسون عبر أوامر المحادثة،
ويدير البوت التسجيل والإجابات والترتيب والإعلانات تلقائيًا.

> مبدأ التصميم الأساسي: **لا بيانات مزيفة في أي مكان.** ما لا يعمل يظهر كما هو
> («غير متصل»، «محفوظ — لا اتصال»، «الاشتراك غير مؤكد»)، وما يعمل مبنيًا على قاعدة
> بيانات حقيقية ونداءات فعلية لـ Kick.

## المزايا وحالة كل جزء بصراحة

### مكتملة وتعمل

- **مصادقة داخلية**: تسجيل/دخول بالبريد وكلمة المرور (bcrypt)، جلسات في قاعدة البيانات عبر كوكي `httpOnly`، حماية Middleware مع فحص أصل الطلبات المتغيرة (Origin).
- **إنشاء فعاليات بمعالج 5 خطوات**: النوع (أسئلة / سرعة / فرق) → الأوامر المخصصة → قواعد المشاركة → الإعداد والأسئلة → المراجعة والحفظ، مع تعديل المسودات لاحقًا.
- **محرر أسئلة**: اختيار من متعدد (حروف A–D / أ–د) أو إجابة حرة، نقاط ومكافأة سرعة وزمن لكل سؤال، وتحقق من صحة الإعداد قبل الجاهزية.
- **دورة حياة كاملة على الخادم**: `DRAFT → READY → REG_OPEN → REG_CLOSED → RUNNING → COMPLETED/CANCELLED` — الانتقالات تُفرض في المحرك، لا في الواجهة.
- **خط أوامر موحّد**: رسائل Webhook الحقيقية ورسائل المحاكي تمر بنفس الممر تمامًا (تنقية الإيموتات → تحليل الأمر → حدود المعدل → التحقق من الصلاحية والمواعيد → التنقيط).
- **تنقيط حتمي**: أول إجابة صحيحة تأخذ مكافأة السرعة، حدود محاولات لكل جولة، فك تعادل (أسبقية التسجيل / أكثر جولات فائزة / تعادل)، فوز الفرق بحساب مجموع الأعضاء.
- **غرفة تحكم حية**: تحديث لحظي عبر SSE مع تراجع تلقائي للاستطلاع (polling) عند فشل الدفق، شريط تحكم بصلاحيات حسب الحالة، لوحة ترتيب وأجوبة حية وسجل نشاط وصندوق إعلانات بحالات حقيقية (PENDING/SENT/BLOCKED/FAILED مع سبب الفشل).
- **صندوق إعلانات (Outbox)**: كل رسالة بوت تُؤرشف قبل الإرسال مع محاولات وإعادة جدولة وتقديم تدريجي عند 429 وحد داخلي آمن بين الرسائل (1200ms افتراضيًا — Kick لا توثق حدًا رقميًا).
- **محاكي مدمج ومعزول**: يتطلب `simulation` مفعّلة بالفعالية نفسها ومحدد بمعدل (30 طلب/دقيقة/فعالية) — لا يمكن الخلط بين بيانات الاختبار والفعاليات الحقيقية (شارة «وضع اختبار» تلاحق كل شاشة).
- **أرشفة كاملة**: سجل عمليات (Audit) لكل فعل إداري/تلقائي، ونتائج نهائية محفوظة (ترتيب + فائز + مجموع فرق) قابلة للعرض دائمًا حتى بعد الإنهاء.
- **تشفير الاعتمادات**: رموز OAuth مخزنة مشفرة AES-256-GCM، وتحديث تلقائي للرمز عند انتهائه،
  وفصل (Disconnect) يحاول ردّ (revoke) الرمز لدى Kick كأفضل جهد، يحذف الاشتراكات ثم التخزين.
- **نظام يصمد أمام إعادة التشغيل**: المواعيد والحالات كلها في قاعدة البيانات؛ حلقة الجدول (tick) تكمل ما انقطع: جدولة فتح/إغلاق التسجيل، وحسم الجولات انقضت مواعيدها تلقائيًا.

### جزئية

- **تخصيص رسائل البوت**: قوالب كل فعالية قابلة للتعديل بالكامل (مع عداد 500 كتية حرفًا)، وإعدادات بوت على مستوى القناة (الاسم، نوع الإرسال user/bot، فاصل الرسائل، الرد على الأفراد) — تعمل، لكن لا يوجد محرر قوالب «عام» خارج الفعاليات.
- **لوحة الفرق**: توزيع آلي متوازن + انضمام بالأمر المخصص + مجموع الأعضاء والنقاط — لكن تبديل الفريق بعد قواعد الإعداد يُرفض كما هو مُعد (السماح/المنع) ولا توجد إدارة يدوية لأعضاء الفرق.
- **WebSocket مباشر**: SSE فقط (بحدود زمنية 350ms للقطة ونبضة كل 15 ثانية)؛ لا يوجد WS خالص.

### تحت الظروف الأمثل فقط (مُوثّقة، غير قابلة للاختبار بدون بيانات مطوّر حقيقية)

- **الاتصال الحقيقي بـ Kick**: كل المسار مُنفَّذ (OAuth 2.1 + PKCE عبر `id.kick.com`، تبديل الرمز، التشفير، الاشتراك في `chat.message.sent v1`، التحقق بتوقيع RSA PKCS1v15-SHA256 مرتّبًا على `messageId.timestamp.body`، ونداءات `chat` و`users`) — لكن **لا يمكن التحقق الفعلي منه بدون `KICK_CLIENT_ID/SECRET` حقيقية ورابط عمومي**. حينها فقط يختفي «غير متصل» ويظهر الاتصال الصحيح بعد فحص حيوي فعلي.

## التشغيل السريع

```bash
# 1) المتطلبات: Node 20+
# 2) التبعيات (postinstall يشغّل prisma generate تلقائيًا)
npm install

# 3) البيئة
cp .env.example .env
#   - DATABASE_URL="file:./prisma/data.db"   (كافية للتطوير)
#   - ولّد السرّين:
openssl rand -hex 32   # ضعه في APP_ENCRYPTION_KEY
openssl rand -hex 32   # ضعه في SESSION_SECRET

# 4) قاعدة البيانات (يختار SQLite أو PostgreSQL حسب DATABASE_URL)
npm run db:migrate

# 5) التشغيل (يولّد عميل Prisma المناسب تلقائيًا)
```

بعد فتح الموقع: **أنشئ حسابًا** — يُنشأ تلقائيًا «قناة اختبار محلية» (`kind: LOCAL`)
تتيح كل وظائف المنصة (بما فيها المحاكي) بدون أي حساب Kick.
الحقيقة الشفافة: رسائل بوت هذه القناة **لا تُرسل لأي مكان** وتبقى في صندوق الإعلانات
بحالة `BLOCKED` مع سبب واضح.

## ربط قناة Kick

> كل ما يلي يتطلب عنوانًا عموميًا قابلًا للوصول من الإنترنت (ليس localhost)،
> وتفويض مطوّر من بوابة Kick. بدونها تبقى القناة «غير متصلة» بالإخلاص.

1. أضف للمتغيرات:
   ```env
   KICK_CLIENT_ID=...
   KICK_CLIENT_SECRET=...
   APP_BASE_URL=https://your-domain.example
   ```
2. في إعدادات تطبيق Kick سجّل **Redirect URI**:
   `{APP_BASE_URL}/api/kick/callback`
3. اطلب النطاقات المطلوبة (تُطلب أثناء التفويض وتُفحص بعد الربط):
   للدقة، القائمة الفعلية في الشيفرة: `src/server/kick/client.ts` → `SCOPES_TO_REQUEST` / `REQUIRED_SCOPES`.
4. اضغط «ربط قناة Kick» من صفحة **ربط Kick** — تبادل الرمز يحدث على الخادم، والرموز تُخزَّن مشفرة،
   ويحاول الخادم إنشاء اشتراك Webhook فورًا، ثم يُعاد الرد على الواجهة بحالة صادقة
   (متصلة / متصلة لكن ناقصة نطاقات / متصلة لكن الاشتراك غير مؤكد / خطأ مع سببه).
5. تظهر النطاقات الممنوعة والناقصة والفحص الحيوي وقطع الاتصال في نفس الصفحة.

**مهم:** لا يوجد نداء برمجي لتعيين Webhook في Kick — يُضبط يدويًا في إعدادات تطبيق المطوّر.

## Webhook

- **المسار**: `POST {APP_BASE_URL}/api/kick/webhook`
- **معالجة الطلب بالترتيب**:
  1. رؤوس كاملة (`Kick-Event-Message-Id`, `-Signature`, `-Message-Timestamp`, `-Type`, `-Version`).
  2. التوقيع: RSA PKCS1v15-SHA256 على `messageId.timestamp.rawBody` بمفتاح عام من
     `GET /public-v1/public-key` (مع تخزين مؤقت 10 دقائق وفرض تحديث عند فشل التحقق).
  3. عدم التكرار عبر `WebhookIngest` (معرّف الرسالة) — إعادة الإرسال لا تكرر أي أثر.
  4. السياسة: الرد `204` عند تجاهل الحدث بهدوء (حدث غير مشترك أو خارج سياق فعالية نشطة)،
     والرد بخطأ عند فشل مؤقت كي يعيد Kick الإرسال لاحقًا.
- طلب **بدون توقيع صالح = 401** دائمًا.
- الرسائل الواردة تُنقّى (إزالة `[emote:id:name]`) ثم تدخل خط الأوامر الموحّد.

## دورة حياة الفعالية

| الحالة | معناها | المتاح منها |
|---|---|---|
| `DRAFT` | مسودة | تعديل/حذف/جهّز/إلغاء |
| `READY` | مُعدة وجاهزة | رجوع لمسودة/فتح تسجيل/بدء مباشر/إلغاء |
| `REG_OPEN` | التسجيل مفتوح | إغلاق التسجيل/إلغاء — المشاهدون `!join` |
| `REG_CLOSED` | التسجيل مغلق | إعادة فتح/بدء البث/إلغاء |
| `RUNNING` | بث حيّ | إيقاف مؤقت/استئناف/تقدم جولة/إنهاء/إلغاء |
| `COMPLETED` / `CANCELLED` | أرشيف | قراءة فقط (النتائج والصندوق والسجل) |

- **فعالية نشطة واحدة لكل قناة** (REG_OPEN أو RUNNING) — يُمنع فتح أخرى حتى تنتهي.
- **البدء الحقيقي للبث لا يحدث تلقائيًا أبدًا**؛ زر «البدء» في غرفة التحكم يغلق التسجيل
  ويُشغّل الجولة الأولى (أو زر البدء المباشر من `READY`).
- إنهاء الفعالية بلا مشاركين مسجلين → `NO_PARTICIPANTS` (بلا فائز مزيف).
- إيقاف مؤقت يجمّد موعد الجولة ويُقاس الاسترداد بتتبع الوقت المتبقي دون إعادة العدّ من الصفر.

## أوامر المحادثة

أوامر كل فعالية قابلة للتخصيص (بادئة `!` + حتى 20 محرفًا، دون فراغات):

| الأمر الافتراضي | الوظيفة | القيود المُفرضة |
|---|---|---|
| `!join` | التسجيل | مرة واحدة افتراضيًا (`joinOnce`) + حد أقصى اختياري (`maxParticipants`) + خيار الانضمام بعد البدء (`lateRegistration`) |
| `!leave` | الانسحاب | المُسجلون فقط؛ المُزالون (REMOVED) لا يعودون |
| `!answer <x>` | الإجابة | من المسجلين النشطين فقط + خلال موعد الجولة + ضمن حد المحاولات |
| `!team <اسم>` | الانضمام لفريق | حسب إعداد الفرق؛ يمكن منع التبديل/الانضمام بعد بدء البث (`joinAfterStart`) |
| `!score` | ترتيب المشاهد نفسه | للنشطين |
| `!event` | حالة الفعالية | معلومات عامة فقط؛ لا تسريب للإجابة الصحيحة |
| `!help` | المساعدة | تعرض الأوامر الفعلية المُعدة لهذه الفعالية |

الحد الزمني للمعدل على مستوى خط المعالجة: **حصة لكل مشاهد** (`COMMAND_RATE_LIMIT`)
+ حد إرسال داخلي للبوت مع تراجع تلقائي عند `429` (يقرأ `Retry-After` عند وجوده).
التطبيع العربي (الهمزات/التاء المربوطة/التشكيل) يُطبق على الإجابات الحرة، وحساسية
الحالة مُعدة لكل فعالية.

## وضع الاختبار

- يُفعَّل **لكل فعالية على حدة** عند الإنشاء (شارة ظاهرة في كل الشاشات + في قوائم النتائج).
- يمر عبر `POST /api/events/[id]/simulate` مع تحقق صلاحية المالك وحد 30 طلب/دقيقة.
- مستخدمو المحاكي أرقام معرفات بعيدة عن نطاقات Kick الحقيقية (توليد حتمي من اسم المستخدم).
- رسائل بوت القناة المحلية: `BLOCKED` مع سبب «لا اتصال» — لا ادعاء إرسال.

## النشر للإنتاج

```bash
npm run build
npm start       # أو pm2/systemd — الأفضل خلف nginx مع TLS
```

- **قاعدة البيانات**: المشروع يدعم SQLite (تطوير/اختبارات) وPostgreSQL (إنتاج) تلقائيًا
  حسب `DATABASE_URL`:
  - إذا بدأ الرابط بـ `postgresql://` أو `postgres://` يستخدم المشروع
    `prisma/postgres/schema.prisma` وترحيلات `prisma/postgres/migrations`.
  - وإلا يستخدم `prisma/schema.prisma` وترحيلات SQLite.
  - مصدر الحقيقة هو `prisma/schema.prisma`؛ نسخة PostgreSQL مولّدة تلقائيًا
    عبر `npm run db:sync:pg` (يشغّلها البناء والبدء تلقائيًا). لا تعدّلها يدويًا.
  - عند تعديل المخطط: شغّل `npm run db:migrate` مرة برابط SQLite (لترحيلات الاختبارات)
    ومرة برابط PostgreSQL (لترحيلات الإنتاج).
- **أوامر النشر**:
  ```bash
  npm run build     # يولّد Prisma Client المناسب ثم يبني Next.js
  npm start         # يطبّق ترحيلات الإنتاج ثم يشغّل الخادم
  ```
  إن أردت تطبيق الترحيلات يدويًا: `npm run db:deploy`.
- **Aiven Free PostgreSQL** خيار مجاني بدون بطاقة: 1 GB تخزين و20 اتصالًا؛
  أضف `connection_limit=5` إلى الرابط وشغّل نسخة واحدة من التطبيق.
- **APP_BASE_URL** يجب أن يكون العنوان العمومي الصحيح (يبني منه Redirect وWebhook).
- تشغيل الجدول تلقائي عبر `src/instrumentation.ts` عند إقلاع الخادم (لا cron خارجي مطلوب).
- في Production يُفرض وجود `SESSION_SECRET` عند الإقلاع، وغياب مفاتيح Kick يجعل زر «ربط»
  معطلاً برسالة تشرح السبب — ولا يتظاهر النظام بالاتصال أبدًا.

## استكشاف الأخطاء

| العرَض | السبب/الحل |
|---|---|
| زر «ربط قناة Kick» غير موجود | `KICK_CLIENT_ID/SECRET` غير مضبوطة أو الخادم لم يُعاد تشغيله بعد ضبطها |
| «غير متصلة» بعد الربط | افحص صفحة ربط Kick: رسالة آخر خطأ من الفحص الحيوي معروضة كما هي |
| «نطاقات ناقصة…» | أعِد الربط بعد إضافة النطاقات المطلوبة في تطبيق Kick؛ القائمة تظهر في الصفحة |
| «اشتراك الأحداث غير مؤكد» | Webhook URL غير مضبوط في إعدادات تطبيق Kick أو عنوان غير عمومي — صحّحه ثم «فحص الاتصال الآن» |
| رسائل البوت لا تصل لكت | راقب صندوق الإعلانات: `FAILED` يعرض خطأ النداء، و`BLOCKED` بسببه (قناة محلية/نص أطول من 500) |
| تراجع رسائل متتالية | بترميز `429` يقرأ `Retry-After` ويبطّئ تلقائيًا للقناة نفسها؛ الفاصل الأدنى مُعد في الإعدادات |
| Webhook يرد 401 | توقيع غير صحيح أو رؤوس ناقصة أو جسم تعرّض لإعادة ترميز — وراء reverse proxy لا تُعدّل الجسم (لا gzip/إعادة ترميز) |
| SSE لا يعمل وتراج الواجهة لتحديثات بطيئة | هذا هو التراجع المُعد (polling كل 15 ثانية)؛ افحص أي بروكسي يقطع تدفقات `text/event-stream` |

---

## القيود المعروفة

1. **لا حصة إرسال موثقة من كت** — الحد الداخلي (1200ms) افتراض آمن مع تراجع عند 429.
2. **لا نداء برمجي لتعيين Webhook** — خطوة يدوية في بوابة المطوّر.
3. **التحقق الحقيقي من اتصال Kick** يتطلب مفاتيح مطوّر فعلية وعنوانًا عموميًا؛ حتى ذلك الحين
   تعرض المنصة الحالة الصادقة بدل ادعاء الاتصال.
4. جلب الرسائل القديمة (backfill لما قبل الاشتراك) غير متاح — الأرشيف يبدأ من لحظة الاشتراك.
5. رموز الإيموت `[emote:id:name]` تُزال كاملة قبل تحليل الأوامر (تفادي الحمولات المخفية داخلها).
6. لغة الواجهة عربية فقط حاليًا (RTL) — إضافة EN تتطلب طبقة ترجمة لاحقًا.
